## 개요

| 항목 | 내용 |
|------|------|
| 문제 | Dreamhack `rev-basic-0` |
| 분야 | Reverse Engineering |
| 분석 대상 | `chall0.exe` |
| 분석 도구 | Ghidra |
| 핵심 주제 | 문자열 참조, Xref, `strcmp`, 조건 분기 기반 입력 검증 루틴 분석 |

이 문서는 Dreamhack `rev-basic-0` 문제를 대상으로 한 리버스 엔지니어링 학습 기록이다.
목표는 단순히 정답을 찾는 것이 아니라, 입력 검증 루틴을 어떤 근거로 식별했는지 정리하는 것이다.

---

## 문제 이해

문제는 사용자 입력을 받아 내부 검증 로직을 통과하면 `correct`, 실패하면 `wrong` 흐름으로 이동하는 입력 검증형 리버싱 문제다.

이 유형에서 중요한 분석 포인트는 다음과 같다.

- 성공 문자열이 어디서 참조되는가
- 입력값이 어느 함수로 전달되는가
- 비교 함수 또는 비교 루틴이 무엇인가
- 비교 결과가 어떤 조건 분기로 이어지는가
- 최종 성공 조건을 어셈블리와 디컴파일 결과로 교차 검증할 수 있는가

---

## 분석 절차

### 1. Ghidra에 바이너리 로드

`chall0.exe`를 Ghidra에 로드한 뒤 자동 분석을 수행했다.
초급 입력 검증 문제는 문자열 참조가 강한 힌트가 되는 경우가 많기 때문에, 먼저 문자열 기반으로 성공 경로를 추적했다.

### 2. 성공 문자열 검색

Ghidra의 `Search -> For Strings` 기능으로 `Correct` 문자열을 검색했다.

성공 문자열은 보통 다음 중 하나의 위치에서 참조된다.

- `main` 함수 내부
- 입력 검증 함수 호출 직후의 성공 분기
- 별도의 출력 함수

이번 문제에서는 `Correct` 문자열 참조를 따라가면서 입력 검증 이후의 성공 경로를 확인할 수 있었다.

### 3. Xref로 사용 위치 추적

`Correct` 문자열이 참조되는 위치에서 우클릭 후 `References` 기능을 사용해 해당 문자열을 사용하는 코드 위치를 확인했다.

문자열 검색 자체보다 중요한 것은 문자열의 주소가 아니라 **그 문자열을 사용하는 코드 흐름**이다.
성공 문자열을 출력하는 위치 주변에는 대개 성공/실패를 가르는 조건 분기가 존재한다.

### 4. `strcmp` 사용 지점 확인

참조 흐름을 따라가며 `strcmp`가 사용되는 위치를 확인했다.
문자열 비교 기반 입력 검증에서는 `strcmp`의 반환값 의미가 핵심이다.

```c
strcmp(a, b) == 0
```

위 조건은 두 문자열이 같다는 의미다.
따라서 `strcmp` 호출 이후 반환값이 `0`인지 확인하는 분기가 성공 조건의 근거가 된다.

### 5. 조건 분기 확인

`strcmp` 호출 이후 인근의 `JZ` 분기를 확인했다.

`JZ` 또는 `JE`는 Zero Flag가 설정된 경우 이동한다.
`strcmp` 결과가 `0`이면 Zero Flag가 설정되므로, 이 분기가 성공 경로인지 실패 경로인지 확인하는 것이 중요하다.

이 단계에서 단순히 디컴파일 결과만 보지 않고, 실제 분기 방향을 함께 확인해야 한다.

---

## 핵심 검증 함수

Ghidra에서 다음 형태의 검증 함수를 확인했다.

```c
bool FUN_140001000(char *param_1)
{
  int iVar1;

  iVar1 = strcmp(param_1, "Compar3_the_str1ng");
  return iVar1 == 0;
}
```

이 함수는 입력값 `param_1`과 고정 문자열을 비교하고, 두 문자열이 같을 때 `true`를 반환한다.

분석 관점에서 핵심은 다음이다.

- `param_1`은 사용자 입력으로 추정된다.
- 두 번째 인자는 바이너리 내부에 저장된 비교 대상 문자열이다.
- `strcmp` 반환값이 `0`이면 두 문자열이 같다.
- 반환값 비교 결과가 이후 성공/실패 분기를 결정한다.

---

## 판단 근거

이번 분석에서 성공 조건을 판단한 근거는 다음과 같다.

1. `Correct` 문자열 참조를 통해 성공 출력 경로를 찾았다.
2. 성공 경로 인근에서 조건 분기를 확인했다.
3. 조건 분기 이전에 `strcmp` 기반 검증 함수가 호출되는 흐름을 확인했다.
4. 검증 함수 내부에서 사용자 입력과 고정 문자열을 비교하는 구조를 확인했다.
5. `strcmp` 반환값이 `0`일 때 `true`가 반환되는 것을 확인했다.

즉, 최종 입력 조건은 단순 문자열 검색 결과가 아니라 **문자열 참조, 함수 호출, 비교 함수, 조건 분기**가 연결된 흐름을 근거로 도출했다.

## 분석 방법 평가

이번 문제에서 사용한 접근은 입력 검증형 리버싱 문제에 적합한 정석적인 흐름이다.

좋았던 점:

- 성공 문자열에서 시작해 빠르게 성공 경로를 찾았다.
- Xref를 사용해 문자열의 실제 사용 지점으로 이동했다.
- `strcmp` 호출을 기준으로 검증 루틴을 식별했다.
- `JZ` 분기를 확인해 성공/실패 흐름을 검증했다.

다음 분석에서 보완할 점:

- 함수명뿐 아니라 VA/RVA 주소를 함께 기록한다.
- `strcmp` 호출 주소를 기록한다.
- 호출 직전 인자 전달 레지스터를 확인한다.
- Windows x64 기준으로 `RCX`, `RDX`에 어떤 값이 들어가는지 확인한다.
- `JZ`가 성공 경로로 가는지 실패 경로로 가는지 명확히 기록한다.

## 한계와 다음 학습 포인트

이번 문제는 비교 문자열이 평문으로 존재하고 `strcmp` 호출이 명확하게 보이는 유형이다.
하지만 난이도가 올라가면 다음과 같은 변형이 등장할 수 있다.

- 문자열이 암호화되어 런타임에 복호화됨
- `strcmp`가 아니라 바이트 단위 비교 루틴이 사용됨
- 비교 함수가 인라인되어 API 호출로 보이지 않음
- 입력값이 변환, XOR, 덧셈, 회전 연산 등을 거친 뒤 비교됨
- 성공/실패 문자열이 제거되거나 난독화됨

따라서 이후에는 문자열 검색만으로 끝내지 않고, 입력 데이터가 어떤 연산을 거쳐 조건 분기로 이어지는지 추적해야 한다.

## 정리

`rev-basic-0` 분석을 통해 문자열 참조 기반으로 성공 경로를 찾고, `strcmp`와 조건 분기를 근거로 입력 검증 루틴을 복원했다.
이번 분석은 기본적인 입력 검증형 바이너리에서 사용할 수 있는 빠르고 실용적인 접근이며, 다음 단계에서는 연산 기반 검증 로직과 자료형 해석 문제로 확장한다.
